# Interface languages

AITU Career uses i18next and react-i18next with locally bundled `kk`, `ru` and
`en` dictionaries in `frontend/src/i18n/locales/<language>/translation.json`.
Keys use section prefixes such as `dashboard.*`, `portfolio.*` and `errors.*`.
The same components and routes serve all languages.

## Preferences and rendering

The initial language is the saved `aitu-career.language` local-storage preference,
then the first supported browser language, then English. Missing translations
fall back to English. Storage failures do not prevent language switching.
The selection survives navigation, reloads, sign-out and sign-in in the same
browser. It is a device preference; no database migration or account preference
API was added. Storage events synchronise other tabs.

`LanguageSwitcher` appears in public and authenticated headers and inside modal
headers. Changes update React translations, the document language, title and
description without navigating or remounting forms. Input values, filters and
open editors remain intact.

Use `useI18n()` for `t`, `number`, `date`, `list`, `enumLabel`, `sourceLabel`,
`matchExplanation` and `message`. `Intl` formats dates and numbers for `kk-KZ`,
`ru-RU` and `en-GB`. Date-only API values are parsed as local calendar dates to
avoid shifting the day. Native date editors retain ISO values for API submission.
The Manrope / Segoe UI font stack supports Cyrillic and Kazakh characters.

## Data and errors

Translate static text with keys and interpolate complete sentences. Do not join
translated grammatical fragments to construct headings or messages.
Keep notification keys in component state and translate at render time so an
already visible notification changes language too.

API enum values remain unchanged (`Full-time`, `Internship`, etc.); only their
display labels are translated. Technical skills, company names, official role
names, catalogue content and user-authored text remain in their original
language because the database has no localized content fields.

Known backend system messages and Pydantic validation responses are mapped in
the frontend adapter. Unknown server messages remain verbatim. Profile
improvement messages and competency evidence prefixes have explicit adapters.
Readiness and match explanations use the existing numeric assessment data;
there is no runtime machine translation or generated replacement score.
There is no conversational AI recommendation endpoint accepting a language.

`LocalizedForms` supplies translated browser constraint-validation messages.
`ConfirmProvider` supplies translated deletion dialogs with localized buttons.

## Adding translations and checking changes

Add each key and its interpolation parameters to all three dictionaries, then
reference it with `t('section.key', { parameter: value })`. Avoid translating
payload identifiers, URLs or database values. If a new backend system message is
introduced, add its explicit mapping and translations.

From `frontend/`:

```text
npm run check:i18n
npm run build
npm run test:e2e
```

The dictionary check validates key parity, nonempty translations, interpolation
parameters, static translation references and untranslated Cyrillic JSX text.
Browser tests cover all three languages, main routes, server and client errors,
input preservation, modal forms, deletion cancellation, persistence, browser
fallbacks, mobile layout, authorization and the original application workflows.
