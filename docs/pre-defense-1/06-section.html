6.1 Priorities and traceability

MoSCoW priorities: Must denotes mandatory MVP behavior; Should denotes a planned improvement; Could denotes an optional extension. An implemented feature is not evidence that users need it. Requirement IDs connect the specification, components, tasks and verification.

6.4 Matching and readiness rules

Score = 100 × Σ(weight × contribution) / Σ(weight). For an explicit skill, contribution = min(1, user_level / required_level); for an absent skill it is zero. Inferred text and semantic evidence are capped at 0.5. Required/preferred skill weights default to 2/1 and may be set to other positive values. Scores across different vacancies do not imply equal job difficulty.

Readiness is an internal heuristic: market 60%, projects 15%, experience 10%, certificates 5% and education 10%, with configurable normalized weights. Market uses up to five highest-scoring target-role vacancies; relevant experience is capped at 180 non-overlapping days. These weights have not been empirically validated as predictors of employment.

6.5 AI functionality and implementation status

The implemented decision-support baseline is deterministic: it extracts known skill terms and aliases, combines profile evidence, scores vacancy requirements and derives gap-based actions. This is a knowledge-based matching pipeline, not a trained employment predictor or a generative assistant. The learned AI extension is a local sentence-embedding adapter; it is disabled in the verified configuration. The report therefore separates working rule-based functionality from available but unevaluated machine-learning functionality.

6.6 Worked example

Illustrative calculation: Python level 3 of required 3 with weight 2 contributes 2; SQL level 1 of required 2 with weight 2 contributes 1; absent Git with weight 1 contributes 0. The score is 100 × (2 + 1 + 0) / (2 + 2 + 1) = 60%. Python is matched, SQL is partial and Git is missing.

Implementation reference: https://github.com/vbl0-0/AITU-Career/blob/prob-period-1/backend/app/ai/matching.py. Matching correctness tests verify rules and boundaries. Only an independent relevance experiment can establish whether this approach ranks useful vacancies better than simpler alternatives.
