5. Technology Comparison

5.1 Technology alternatives

The alternatives are assessed for a small educational prototype with a Python analysis module, relational data and no interaction history. Assessments are qualitative; no unperformed performance measurements are implied.

Table 5.1. Technology alternatives
DecisionReasonable alternatives and trade-offsSelected solution and rationale
Backend platformFastAPI: validation/OpenAPI and direct Python NLP integration [S15]. Django REST: mature conventions and administration, with a larger framework surface. Node.js/NestJS: a shared frontend language, but Python NLP needs an additional integration boundary.FastAPI supports one small API/analysis process and a modular code structure.
Data storagePostgreSQL: relational constraints and transactions [S16]. SQLite: simple setup with a different concurrency/operation profile. MongoDB: flexible documents, with a different strategy for cross-record integrity.PostgreSQL with SQLAlchemy and Alembic preserves linked profiles, catalog entries and vacancy requirements.
Matching approachExact matching: transparent but sensitive to wording. Dictionary/aliases/weights: explainable but requires catalog maintenance. Embedding hybrid: supports paraphrases [S07–S09] but adds calibration and inference cost.Weighted normalized keyword matching is the default; embeddings remain optional and require separate evaluation.
Component communicationREST/JSON: straightforward CRUD and OpenAPI. GraphQL: flexible selections with an additional schema/cost-control layer. gRPC: typed binary communication but more integration work for a browser client.REST/JSON under /api, with Vite/nginx proxying to a single browser origin.
FrontendReact/TypeScript: typed components already implemented. Vue/TypeScript: a comparable SPA option requiring component migration. Server templates: a smaller client stack but a different approach to interactive profile editing.React/TypeScript with Vite follows the implemented journeys; no unmeasured speed advantage is claimed.

5.2 Architectural decisions

ADR-01: use a modular monolith. Authorization, API, analysis and persistence have separate code responsibilities but share one backend deployment. Revisit separation only if profiling demonstrates interference from inference. ADR-02: PostgreSQL is the source of truth; preserve algorithm version and input revisions with saved analyses. ADR-03: absence of the optional model must not break keyword analysis.
